# Alert ingestion contract and recovery

## Normalized event

Collectors emit `schema_version: 1.0.0` records with `event_id` (and legacy `id`), `source_type`, `source_sensor`, `source_event_timestamp` (and legacy `timestamp`), `received_timestamp`, categorical `severity`, optional source-native `severity_level`, `rule_id`, optional source/destination IPs, `description`/`event_type`, and the original structured event in `evidence`. Existing fields such as `wazuh_rule_id`, `agent_id`, `suricata_signature_id`, `risk_score`, and `raw_log` remain available to the investigator. Missing IPs or sensor identifiers remain null; they are not invented. Synthetic scenario inputs use `source_type: simulated` and are distinguished from live sensor events.

## Wazuh

Manager and indexer credentials are read only from `WAZUH_USER`/`WAZUH_PASSWORD` and `WAZUH_INDEXER_USER`/`WAZUH_INDEXER_PASSWORD`. There are no credential defaults. TLS verification defaults to enabled; set `WAZUH_CA_BUNDLE` to a trusted CA bundle when needed. Configure page size and maximum pages to bound each pull. Requests have timeouts, bounded retries for timeouts, connection failures, 429, and 5xx responses. Authentication, TLS, HTTP, and checkpoint failures are represented by non-sensitive error codes; credentials, tokens, and alert bodies are not logged.

Manager `/alerts` is retained as the existing configurable API path (`WAZUH_ALERTS_PATH`). The indexer uses `POST /wazuh-alerts-*/_search` with bounded `from`/`size` pagination and a time-window filter. Wazuh documents the `_search` path for querying stored alerts; `from`/`size` pagination has not yet been verified against the lab’s exact version or data mapping. The repository Compose file pins `4.12.0`, but the running lab version is unknown. A read-only lab test must confirm the configured account is restricted to alert search.

`WAZUH_CHECKPOINT_PATH` stores a bounded set of acknowledged IDs and a durable `pending_events` queue. Newly normalized events are atomically added to the pending queue before they are returned. Repeated polls redeliver pending events; they are moved to the acknowledged-ID set only after the executor closure successfully saves the incident to SQLite. If the queue is full, collection fails visibly without replacing the checkpoint. This is at-least-once delivery, not a cross-store transaction; a crash after SQLite commit but before checkpoint acknowledgment can replay an event, so consumers must deduplicate by stable `event_id`. Events outside the configured lookback or beyond the configured page cap can be missed; monitor page-cap metadata and configure a window/cap suited to the lab workload.

## Suricata

`SURICATA_EVE_PATH` points to the EVE JSONL alert log. The collector reads complete newline-terminated records from a byte offset, retains an incomplete trailing record for the next poll, skips malformed/oversized records with counters, and limits work per poll. Stable IDs use EVE identifiers when present or a SHA-256 identity of the canonical event. The checkpoint atomically stores the file identity, byte offset, bounded acknowledged-ID set, and durable pending events. Pending events are redelivered until an incident is successfully saved and the executor acknowledges their IDs. If the pending queue is full, the file cursor is not advanced. Rotation replacement/truncation resets the offset; copy-truncate with the same file identity is detected when the file is shorter than the saved offset.

Checkpoint advancement is protected by durable pending-event storage and acknowledgment after incident persistence. It is still at-least-once: an event may be replayed if the process stops after SQLite commit but before its checkpoint acknowledgment. Incident persistence failures leave pending events unacknowledged for recovery. No alert payloads are written to logs; checkpoints contain original event evidence and must remain local and access-controlled.

## Environment and live lab test

Copy `.env.example` to a local `.env`, then configure only authorized lab endpoints and a least-privilege read-only Indexer account. The repository’s Compose file pins Wazuh Manager and Indexer images to `4.12.0`; this is not proof of the version running in an external lab. Current Wazuh documentation describes searching the `wazuh-alerts-*` index through the Indexer API. Confirm the lab’s account permissions and trusted TLS chain before use. Do not put credentials, private keys, or raw alert payloads in logs. No live service was contacted for this milestone.

A future live test requires separate approval, a read-only Wazuh user, trusted CA/system certificate configuration, a readable Suricata EVE source, bounded windows and record counts, and a plan to compare event IDs, timestamps, counts, duplicates, and recovery. `scripts/verify_lab_ingestion.py` is an explicit read-only tool: it requires an environment opt-in, three command-line confirmations, and writes only temporary checkpoints under the ignored `data/lab-ingestion-checkpoints/` directory. It never persists incidents or imports notification/response connectors. It must not invoke the response executor, send email, modify EVE, or generate traffic.
